# Running AI-OS for Multiple Clients

## The Key Principle

AI-OS has two layers:

1. **Shared methodology** — `AGENTS.md`, `CLAUDE.md`, `SOUL.md`, skills, scripts. Version-controlled and shared. Lives at the root of your AI-OS folder.
2. **Client data** — `brand_context/`, memory, learnings, projects, cron jobs, local settings, API keys, client-only skills, and `SKILL.local.md` overrides. Unique per client. Lives inside `clients/{client-name}/`.

Claude remains the primary runtime. The compatibility change is structural:
- `AGENTS.md` is now the canonical shared instruction file
- root `CLAUDE.md` imports `@AGENTS.md` for Claude Code
- each client gets its own `AGENTS.md` for client-specific instructions
- each client also gets a thin `CLAUDE.md` wrapper that imports the local `AGENTS.md`

Everyone starts as a solo operator working from the root folder. When you need a second client, run `add-client.sh` and AI-OS creates a client workspace with separate context and outputs.

## How the Shared Instructions Load

### Claude Code

Claude Code reads `CLAUDE.md` files from parent directories. In AI-OS:

```text
AI-OS/
├── CLAUDE.md                    <- imports root AGENTS.md
├── AGENTS.md                    <- canonical shared methodology
└── clients/
    └── client-one/
        ├── CLAUDE.md            <- imports client AGENTS.md
        ├── AGENTS.md            <- client-specific instructions
        └── ...
```

When you `cd clients/client-one && claude`:
- the root `CLAUDE.md` loads and imports the root `AGENTS.md`
- the client `CLAUDE.md` loads and imports the client `AGENTS.md`
- the result is shared methodology from the root plus client-specific instructions from the client folder

### Codex

Codex reads `AGENTS.md` directly, from the repo root down to the current directory.

When you work inside a client folder with Codex:
- root `AGENTS.md` provides the shared methodology
- client `AGENTS.md` provides the client-specific layer

No extra shim is needed for Codex.

## What's Shared vs What's Separate

| What | Where | How clients get it |
|------|-------|-------------------|
| `AGENTS.md` (shared methodology) | Root | Shared directly from the root |
| `CLAUDE.md` (shared wrapper) | Root | Auto-inherited by Claude Code |
| `context/SOUL.md` | Root | Read by Claude heartbeat fallback |
| `context/USER.md` | Root | Read by Claude heartbeat fallback |
| `.claude/skills/` (shared skills) | Root only | Inherited by every client through project-root skill discovery, never copied |
| `scripts/` | Root + each client | Copied on client creation, auto-synced on update |
| `.claude/settings.json`, hooks, hook info, cron templates | Root + each client | Shared system files auto-sync on update |
| `AGENTS.md` (client-specific) | Each client | Created by `add-client.sh` |
| `CLAUDE.md` (client wrapper) | Each client | Created by `add-client.sh` |
| `brand_context/` | Each client | Built automatically on first session |
| `context/learnings.md` | Root + each client | Root is private user learnings in Team OS mode; each client keeps only that client's learnings and should start clean or from a controlled server seed |
| `context/memory/` | Root + each client | Root has system-wide memory; clients keep their own session history |
| `projects/` | Each client | Per-client deliverables |
| `.env` | Each client | Usually copied from root during client creation |
| `cron/jobs/` | Each client | Per-client scheduled tasks |
| `.claude/settings.local.json` | Each client | Personal client settings, preserved during updates |
| Client-only skills and `SKILL.local.md` | Each client | Client-specific skill additions, preserved during updates |
| `.gitignore` | Each client | Generated by AI-OS so regenerated root copies stay out of git |

### What stays in sync automatically

- Shared methodology at the root
- Shared skills, because every client reads them straight from the root and there is no copy to fall behind
- Scripts, hooks, settings, and cron templates when you run `update.sh`
- Claude wrappers and client instruction backfills when `update-clients.sh` runs during updates

### What you manage separately

In Solo mode, a generated `context/current-state.md` gives each client a short
recent summary and links to its own source files. Refresh it at substantive task
startup, then read only the relevant sources. Confirmed corrections also stay in
that client's logs and learnings. Commands and Team boundaries:
[Reliable work](agent-reliability.md).

- Brand context
- Learnings
- Session memory
- Projects
- Cron jobs
- API keys if you want client-specific secrets
- Client local settings
- Client-only skills
- `SKILL.local.md` overrides for shared skills

## Version Control and Backups

Commit client data, not regenerated root copies.

Track these files for private backup:
- `AGENTS.md`, `CLAUDE.md`, and the generated `.gitignore`
- `brand_context/`
- `context/`
- `projects/`
- `cron/jobs/`
- client-only skill folders in `.claude/skills/`
- `SKILL.local.md` files inside shared skill folders

Do not commit the root-copied machinery inside each client. AI-OS regenerates it from the root during updates, and the generated client `.gitignore` keeps it out of `git status`:
- `scripts/`
- `.claude/hooks/`
- `.claude/hooks_info/`
- `.claude/settings.json`
- `cron/templates/`, `cron/logs/`, and `cron/status/`

Shared skills are not on that list because they are never copied into a client. Everything under a client's `.claude/skills/` is client-owned and stays trackable.

If you create a new skill for only one client, create it directly under that client's `.claude/skills/` folder. It is client data and remains visible to git. If a later AI-OS update adds a root skill with the same folder name, `update-clients.sh` preserves the client-owned folder and warns you instead of silently replacing it.

## How Skills Reach a Client

Shared skills live only in the root folder. There is no per-client copy. Claude Code resolves project skills from the enclosing repository root, so a session started in `clients/client-one/` sees the whole root skill pack without anything being copied in.

That is why shared skills never drift: a client reads the same files you edit, so an edit at the root is live in every client immediately, with no sync step.

Always edit shared skills at the root level:

```text
Edit here:     AI-OS/.claude/skills/mkt-copywriting/SKILL.md
Not here:      AI-OS/clients/client-one/.claude/skills/mkt-copywriting/SKILL.md
```

A client's `.claude/skills/` holds only client-owned material: client-only skills and `SKILL.local.md` overrides.

Client-specific changes to a shared skill should go in `SKILL.local.md` next to that skill's `SKILL.md`. Updates never touch it, and it stays trackable in git.

If a client folder was created by an older AI-OS that did copy every skill in, `update-clients.sh` prunes those leftovers. It removes a copy only when the content matches a root version, either the current one or one still recoverable from the repository history, so nothing you wrote can be lost. Anything you edited yourself is kept and reported.

### A client folder depends on the root

Because skills resolve from the enclosing repository root rather than by walking parent folders, a client folder is not self-contained. Copy `clients/client-one/` somewhere outside the AI-OS install and it resolves zero skills. Keep client folders where `add-client.sh` created them.

If you do need to work from a client folder outside the install, start Claude Code with `--add-dir` pointing at the AI-OS root:

```bash
claude --add-dir ~/Projects/AI-OS
```

That loads the root's `.claude/skills/` into the session.

### Stopping one client from inheriting a root skill

Inheritance is all-or-nothing by default, but you can switch off a single skill for a single client. Add it to `skillOverrides` in that client's `.claude/settings.local.json`:

```json
{ "skillOverrides": { "skill-name": "off" } }
```

Merge into the existing JSON rather than replacing the file. If the file does not exist yet, create it with just that content. No script ever overwrites `.claude/settings.local.json`, so the setting survives every update.

New clients inherit the consensus: `add-client.sh` seeds the new client's `settings.local.json` with the overrides shared by every client that has overrides, and reports what it inherited. A client with no overrides abstains rather than vetoing. A skill hidden in only some of the clients that do have overrides stays that client's decision and is not inherited. The file is seeded once at creation; no update changes its content.

Inside that client the skill stops being invocable and disappears from the session. `list-skills.sh` keeps showing it, marked as off for that client in its own Hidden section, so the exclusion stays easy to find and undo. The root and every other client are unaffected. Use `remove-skill.sh` at the root only when you want the skill gone for yourself and for every client.

### Client-only skills

A skill authored at `clients/client-one/.claude/skills/{skill-name}/SKILL.md` exists for that client alone.

One important exception to the usual rule: `docs/building-skills.md` says any new skill on disk should be registered in the skill registry, the context matrix, `context/learnings.md`, and the README. That applies to shared root skills. A client-only skill does not belong in the root catalog, so do not register it there. Document it inside the client instead.

Avoid giving a client skill the same folder name as a root skill. A same-name client skill shadows the root one inside that client and stops receiving root updates, freezing it at the version you wrote. To extend a root skill for one client, use `SKILL.local.md`. To hide one, use `skillOverrides`.

```text
    │   ├── projects/

    └── client-two/
        └── ...
```

### Adding a New Client

```bash
cd ~/Projects/AI-OS
bash scripts/add-client.sh "Client One"
```

This creates `clients/client-one/` with:
- a client `AGENTS.md` for client-specific instructions
- a client `CLAUDE.md` wrapper for Claude Code
- a generated `.gitignore` for client backup behavior
- scripts copied from root
- an empty `.claude/skills/` for client-only skills and `SKILL.local.md` overrides, since shared skills are inherited from the root rather than copied
- learnings seeded from root
- empty `brand_context/`, `projects/`, and `context/memory/` folders
- a copy of `.env` if one exists at the root

Then start working:

```bash
cd clients/client-one
claude
```

Claude automatically detects it's a new client and walks through the brand foundation.

### Using the Root as a Personal Hub

You don't have to give the root a business identity. If you keep the root for personal work and put each company in `clients/`, leave the root `brand_context/` empty:

- once any `clients/*/brand_context/` is populated, root sessions stop offering `/start-here`
- before your first client is set up, say you want to skip when onboarding starts at the root; Claude writes `context/.onboarding-skipped` and won't ask again (delete the file to bring onboarding back)
- each client still runs its own onboarding the first time you open it

### What Claude Sees in a Client Folder

When you `cd clients/client-one && claude`:
1. root `CLAUDE.md` loads and imports root `AGENTS.md`
2. client `CLAUDE.md` loads and imports client `AGENTS.md`
3. Claude heartbeat reads `context/SOUL.md` and `context/USER.md` from the root when needed
4. `brand_context/`, `context/memory/`, and `context/learnings.md` come from the client folder
5. shared skills come from the root `.claude/skills/`, resolved through the repository root, with no copy in the client folder
6. the client's own `.claude/skills/` adds client-only skills and `SKILL.local.md` overrides on top

### What Codex Sees in a Client Folder

When you work in the same folder with Codex:
1. root `AGENTS.md` loads first
2. client `AGENTS.md` loads second
3. the same shared/client layering applies without needing `CLAUDE.md`

## Updating

```bash
cd ~/Projects/AI-OS
bash scripts/update.sh
```

That pulls the latest upstream changes and syncs shared client system files from the root: scripts, hooks, settings, and cron templates. Skills are not in that list because clients read them from the root already.

Updates never overwrite your root or client data. Client context, brand data, memory, projects, cron jobs, `.env`, `.claude/settings.local.json`, client-only skills, and `SKILL.local.md` files are preserved. Shared client machinery is regenerated from root and kept ignored by the generated client `.gitignore`.

Existing clients created before the `AGENTS.md` change are handled conservatively:
- if `AGENTS.md` is missing, `update-clients.sh` seeds it from the old client `CLAUDE.md`
- if the old client `CLAUDE.md` still matches the untouched scaffold, it is replaced with a wrapper automatically
- if the old client `CLAUDE.md` contains custom content, it is preserved and you can clean it up manually later

## Sharing API Keys

If all clients use the same API keys:

```bash
cp .env clients/client-two/.env
```

`add-client.sh` already does this automatically when the root `.env` exists.

## Cron Across Clients

One managed cron runtime covers the root workspace plus every `clients/*` workspace. Start it once from the workspace root:

```bash
cd ~/Projects/AI-OS
bash scripts/start-crons.sh
```

The Command Centre UI also schedules root and client jobs while the server is running. If the UI and daemon coexist, a shared leader lock in `.command-centre/` ensures only one host schedules jobs at a time.

## Rules of Thumb

- Work from the root folder when you are operating for yourself
- Work from `clients/{slug}/` when you are operating for a specific client
- Edit shared methodology in root `AGENTS.md`
- Keep `CLAUDE.md` files as wrappers; do not put the canonical shared rules there
- Edit shared skills at the root
- Let client `AGENTS.md` files hold client-specific instructions
